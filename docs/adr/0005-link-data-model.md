# ADR 0005: Link data model for phase 1

**Status:** Accepted
**Date:** 2026-05-19
**Decision-makers:** Zubair Khalid

## Context

Tidda's first product feature is anonymous URL shortening. A visitor
submits a destination URL, the backend generates a short token, stores
the mapping, and later resolves that token to redirect the browser.

Phase 1 has no authentication, no accounts, no API keys, no custom
slugs, no private links, and no claimable anonymous links. Abuse
protection will be handled through backend rate limiting, initially
using request identity such as IP address in Redis. That abuse identity
is not a durable product owner.

We need a data model that is small enough for the first vertical slice,
but does not block later phases such as click analytics, authenticated
links, API access, or abuse reporting.

## Decision

Model the product concept as a **Link**.

Use a `links` table with these fields in phase 1:

```text
links
  id uuid primary key
  slug text not null unique
  destination_url text not null
  created_at timestamptz not null default now()
```

`id` is the internal database identity. `slug` is the generated public
token used in the short URL. `destination_url` is the URL the service
redirects to. `created_at` is generated by the database.

Anonymous links are ownerless records. Phase 1 will not create an
`anonymous_users`, `anonymous_actors`, or equivalent table, and will not
store an anonymous owner reference on `links`.

In the backend code, the domain model lives under the singular domain
module:

```text
apps/backend/src/link/
```

The HTTP surface can use plural route naming where that reads naturally,
but the domain concept remains singular: `Link`.

## Naming

Use `Link` rather than `Url` for the domain concept. Tidda is not
modelling URLs generally. It is modelling a short link: a generated
slug that resolves to a destination URL.

Use `slug` rather than `short_url` in storage. The full short URL is
derived from the public origin plus the slug. Persisting only the slug
keeps the data portable if the domain changes.

Use `destination_url` rather than `long_url`. The value is not merely a
longer string. It is the redirect destination.

## Why keep an internal `id`

The service could use `slug` as the primary key in phase 1. We rejected
that because `slug` is a public identifier and future tables should not
be coupled to it as their relational reference.

An internal `id` gives later tables a stable reference:

- click events
- analytics rollups
- abuse reports
- audit events
- future ownership records

This keeps slug generation and public URL policy separate from internal
database identity.

## Anonymous ownership

Anonymous links are not claimable later. They remain ownerless forever.

This means phase 1 deliberately avoids durable anonymous identities in
Postgres. Rate limiting can still treat an anonymous request as
`ip:{clientIp}` or another short-lived identity in Redis, but that is
an abuse-control concern, not a data-model concern.

When authenticated links arrive, they can use nullable ownership fields
or a separate ownership table. Existing anonymous links remain records
with no owner.

## Redirects

Do not create a redirect data model in phase 1.

Redirect is a use case over `Link`:

```text
resolve slug
find Link
return destination_url
controller sends redirect
```

There is no `redirects` table and no `Redirect` entity. If route
organisation later benefits from a redirect controller, that controller
should still use the `Link` domain service.

## Alternatives considered

### Use `slug` as the primary key

This is the smallest possible table and would work for phase 1. We
rejected it because future relational data would reference the public
token directly. That makes future slug policy changes more expensive
than they need to be.

### Model anonymous users or actors

This gives anonymous traffic a durable identity, but that is not a
product requirement. It also risks confusing rate-limit identity with
ownership. We rejected it because anonymous links should have no owner.

### Name the model `Url`

This is too broad. A backend may eventually handle many URL-shaped
values: destination URLs, application origins, webhook URLs, preview
URLs, blocked URLs, or allow-list entries. `Link` names the product
concept more precisely.

### Create a redirect entity

Redirects are behaviour, not a separate persisted concept in phase 1.
The only durable object needed to perform a redirect is `Link`.

## Consequences

- The first business table is small and directly supports generated
  short links.
- Anonymous link creation does not create durable anonymous users.
- Future tables can reference `links.id` without depending on the
  public slug.
- The full short URL remains derived at the application boundary.
- Future authenticated ownership requires an additive schema change.
